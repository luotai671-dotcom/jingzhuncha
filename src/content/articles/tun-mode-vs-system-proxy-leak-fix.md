<p class="answer-box"><strong>核心结论速览：</strong>系统代理（System Proxy）仅在应用层注入 HTTP/HTTPS 环境变量，对非标准应用、终端命令（CMD/Git）、UDP 协议及外服游戏完全无效，导致真实公网 IP 直接裸露。TUN 模式通过创建虚拟网络适配器，在操作系统第三层（网络层）捕获并路由所有 IP 数据包，结合 Fake-IP 内核机制可实现系统级无死角全局接管与防泄漏分流。</p>

## 一、 分流失效之痛：为什么开启了客户端依然“漏网”？

在日常使用网络代理工具时，许多开发者与游戏玩家经常遇到这些诡异的现象：
- 浏览器访问海外网站畅通无阻，但在 Windows CMD、PowerShell 或 macOS Terminal 中执行 `git clone` 或 `pip install` 时却频繁超时报错；
- 打开外服网游（如 Steam 联机或暴雪国际服），延迟动辄数百毫秒，甚至直连失败；
- 远程桌面、公司内网穿透（WireGuard / Tailscale）或本地 NAS 在开启代理后突然掉线失联；
- 抓包检查发现，特定客户端软件依然向国内公共 DNS（如 114.114.114.114 或 223.5.5.5）直接发送明文 UDP 53 解析请求，真实地理位置暴露无遗。

这些问题的根源，均在于使用了传统的**系统代理模式（System Proxy）**。只有将分流架构升级至基于内核级的 **TUN 虚拟网卡模式**，并在底层理清路由分流与局域网回环保护，才能彻底杜绝流量漏网与内网瘫痪。

## 二、 底层原理深度拆解：系统代理与 TUN 模式的本质分野

两者的根本差异，在于网络协议栈截获流量的**层级深度（OSI 参考模型）**不同：

```
分流架构对比与 TUN 流量调度拓扑：
┌────────────────────────────────────────────────────────┐
│ 应用程序流量 (浏览器 / Git / 游戏进程 / 命令行终端)        │
└───────────────────────────┬────────────────────────────┘
                            │
         ┌──────────────────┴──────────────────┐
         ▼                                     ▼
[传统系统代理: 应用层 L7]             [TUN 虚拟网卡模式: 网络层 L3]
仅拦截遵循 WinINET 规范的 HTTP/HTTPS   创建系统级虚拟网卡 (wintun / utun)
终端/Git/游戏直连绕过 (漏网!)         捕获所有 TCP / UDP / ICMP 原始数据包
         │                                     │
         ▼                                     ▼
┌──────────────────┐                 ┌───────────────────────────┐
│ 真实公网 IP 泄漏 │                 │ 协议栈转换 (Tun2Socks 引擎) │
└──────────────────┘                 └─────────────┬─────────────┘
                                                   │
                                                   ▼
                                     ┌───────────────────────────┐
                                     │ Fake-IP 映射池 (198.18.0.0/16) │
                                     │ 阻断本地 DNS 污染与递归延迟   │
                                     └─────────────┬─────────────┘
                                                   │
                                     ┌─────────────┴─────────────┐
                                     ▼                           ▼
                        [回环保护: Bypass 局域网]   [核心规则: 域名/GEOIP 分流]
                        (192.168.0.0/16 直连放行)   (根据规则走专线或直连出站)
```

### 1. 系统代理（System Proxy）：被动的应用层协作
在 Windows 下，系统代理主要通过修改注册表中的 `Internet Settings`（ProxyEnable、ProxyServer），通知操作系统上层应用“请使用此代理端口”。然而：
- 该配置只对主动遵循操作系统代理约定的应用生效（如 Edge、Chrome 浏览器）。
- 绝大多数终端开发工具（Git、cURL、Docker）、游戏进程、数据库连接池及 UDP 传输，完全忽略该系统注册表设置，流量直接通过物理网卡网关流出，造成严重的**隐私泄漏与操作超时**。

### 2. TUN 虚拟网卡：霸道的网络层接管
TUN 模式在操作系统内核层创建一块虚拟网卡（在 Windows 下为 Wintun，在 macOS/Linux 下为 utun/tun0）。客户端随后修改系统底层路由表，将默认路由指向这块虚拟网卡。
- 操作系统内任何进程发出的任意数据包（无论 TCP、UDP 还是 ICMP Ping），在离开物理网卡前都会被强行送入 TUN 设备。
- TUN 驱动将捕获到的原始三层 IP 包交由用户空间的 Tun2Socks 引擎解析重组，实现对所有应用、游戏和终端的**绝对无死角接管**。

## 三、 核心配置精要：Fake-IP 模型与局域网回环漏网拦截实操

为了在开启 TUN 全局接管的同时，不破坏本地局域网（LAN）设备互访并彻底防御 DNS 泄漏，必须遵循以下标准化配置规范：

### 1. DNS 模式选型：为什么必须首选 Fake-IP？
传统代理在分流时采用 Redir-Host（系统先解析出真实 IP，再根据 IP 判断走代理还是直连）。这会导致两大弊端：一是本地向公网 DNS 查询容易遭遇 DNS 污染；二是增加一次跨国 DNS 递归查询耗时，延迟翻倍。

**Fake-IP 运行机制**：
- 当应用发起域名查询（如 `api.openai.com`）时，客户端内置 DNS 拦截该请求，直接瞬间返回保留网段中的虚拟伪装 IP（如 `198.18.0.23`）。
- 应用拿到该虚拟 IP 立即向 TUN 发送 TCP 连接请求。
- 客户端在内核对照表中查到 `198.18.0.23` 对应的是 `api.openai.com`，随后将原始域名发送到远程高质量专线节点，由落地机房进行远程纯净 DNS 解析并建立连接。
- 整个过程在本地完全消除了 DNS 解析耗时与污染。

### 2. 局域网回环保护（Bypass Loopback）配置
开启 TUN 模式接管 `0.0.0.0/0` 后，最常见的故障是本地路由器后台、局域网打印机、群晖 NAS 或 WSL2 无法访问。必须在配置中严格设置保留地址绕行：

```yaml
# TUN 模式标准分流保护字段示例
tun:
  enable: true
  stack: system      # 推荐使用 system 或 gvisor 栈
  auto-route: true   # 自动接管默认路由
  auto-redirect: true
  strict-route: true # 阻断网络层漏网包
  
# 局域网直连白名单 (严禁接管本地私网回环)
rules:
  - IP-CIDR,127.0.0.0/8,DIRECT,no-resolve
  - IP-CIDR,10.0.0.0/8,DIRECT,no-resolve
  - IP-CIDR,172.16.0.0/12,DIRECT,no-resolve
  - IP-CIDR,192.168.0.0/16,DIRECT,no-resolve
  - IP-CIDR,198.18.0.0/16,REJECT           # 防止虚拟网段递归冲突
  - GEOIP,CN,DIRECT
  - MATCH,PROXY
```

### 3. 命令行验证命令
在终端中执行以下命令验证 TUN 模式接管状态：

```bash
# Windows PowerShell: 验证默认网关是否被 TUN 虚拟适配器接管
Get-NetRoute -DestinationPrefix "0.0.0.0/0" | Format-Table InterfaceAlias, NextHop, RouteMetric

# 验证终端命令行已完美走代理出站 (无须额外 export http_proxy)
curl -s https://ipinfo.io/json
```

## 四、 故障自救检查表：断网应急三步法与架构选型对比

当客户端发生异常闪退、系统蓝屏后可能导致路由表残留，出现“退出代理后电脑彻底无法上网”的故障。按照以下步骤 3 分钟内即可恢复网络。

### 系统代理模式 vs TUN 模式深度技术特性对比表

| 核心评估维度 | 传统系统代理 (System Proxy) | TUN 虚拟网卡模式 (Wintun) | 推荐核心业务 |
| :--- | :--- | :--- | :--- |
| **网络截获层级** | 应用层 (OSI 第 7 层) | 网络层 (OSI 第 3 层) | — |
| **终端命令行支持** | 默认不支持 (需手动设置 export) | 原生完全支持 (免任何设置) | 软件开发、运维脚本 |
| **外服网游/UDP支持** | 完全不支持 (仅限 TCP) | 原生全面支持 (全端口 UDP) | 联机网游、语音通话 |
| **DNS 泄漏防护** | 较弱 (极易走本地 UDP 53) | 极强 (Fake-IP 内核接管) | 跨境出海、风控防关联 |
| **网络故障几率** | 极低 (仅改注册表) | 低至中等 (依赖虚拟驱动稳定性) | 生产力主机日常使用 |
| **内网设备访问** | 默认不受影响 | 需配置局域网白名单保护 | 智慧家庭、NAS 运维 |

### 故障断网应急自救 SOP（3 步彻底重置网络）：
1. **彻底关闭代理内核进程**：在任务管理器中强制结束代理软件所有残留进程。
2. **管理员运行终端清理残留路由表与 Winsock 目录**：
   ```cmd

   netsh int ip reset
   route -f
   ```

   ```cmd
   ipconfig /flushdns
   ipconfig /renew
   ```

## 五、 延伸深度常见问题（FAQ）

### Q1：Fake-IP 模式下 `ping google.com` 返回 `198.18.x.x` 是不是 DNS 解析异常？
不是异常，这正是 Fake-IP 的正常运行机制。198.18.0.0/15 是 IANA 保留用于网络性能基准测试的内部专用网段。客户端收到该网段的虚拟 IP 后，会在本地将其与域名建立快速映射表，真实的目标 IP 会在经过专线隧道到达境外落地端后再行解析，从而完美避开本地 DNS 劫持。

### Q2：开启 TUN 模式后局域网 NAS、打印机或本地 WSL2 无法访问怎么排查？
这是因为 TUN 网卡的全局默认路由抢占了本地子网优先级。排查步骤：首先检查客户端配置中是否漏掉了 `192.168.0.0/16` 等局域网直连白名单；其次检查 WSL2 的网络模式，建议将 WSL2 配置文件 `.wslconfig` 中的网络模式设置为 `networkingMode=mirrored`（镜像模式），即可与宿主机的 TUN 网卡完美协同。

### Q3：玩外服游戏时开启 TUN 模式延迟依然很高甚至丢包，如何进一步优化？
游戏流量高度依赖短包 UDP 性能与低抖动专线。普通直连公网中转节点在晚高峰存在严重的 UDP QoS 限速。优化方法：一是确保客户端 TUN 模式协议栈选用高性能 `system` 模式而非开销较大的 `gvisor`；二是在节点选择上必须选用带有 IEPL/IPLC 物理内网专线标志的低时延节点。
